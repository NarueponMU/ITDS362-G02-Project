# Performance Testing (Group 02)

เครื่องมือ: **k6** (ทดสอบตอนเขียน script ด้วย v2.3.0) ยิงไปที่ WooCommerce Store API `http://157.85.104.96/shop/wp-json/wc/store/v1`

## พฤติกรรมผู้ใช้ใน script (`lib/shopper.js`)

virtual user (VU) ทุกตัวทำตามขั้นตอนเหมือนลูกค้าจริง แต่ละขั้นมี think time 1–3 วินาที:

1. ดูรายการสินค้า `GET /products?per_page=20`
2. ค้นหาด้วยคำสุ่ม เช่น hoodie, shirt, cap `GET /products?search=…`
3. ดูสินค้าในหมวดแบบสุ่ม `GET /products?category=…`
4. เปิดดูสินค้า 1 ชิ้น `GET /products/{id}`
5. ขอตะกร้าของตัวเอง `GET /cart` แล้วเพิ่มสินค้านั้นลงตะกร้า `POST /cart/add-item`

**ไม่มีการ checkout** ในทุก script ตามที่โจทย์ห้ามสั่งซื้อระหว่าง load test ทุก request มี `check` ตรวจ status และเนื้อหาของ response เช่น ได้ list ของสินค้า, `id` ตรงกับที่ขอ, `items_count` = 1

รอบหนึ่ง (iteration) มี 6 request และใช้เวลาประมาณ 11 วินาทีตอนโหลดปกติ (วัดได้เฉลี่ย 10.7 วินาทีใน average load test) ดังนั้น 1 VU ส่งประมาณ 0.5 request ต่อวินาที

## Script, จำนวน VU, ระยะเวลา และ threshold

| Script | จำนวน VU และระยะเวลา | Threshold | เหตุผล |
|---|---|---|---|
| `average_load_test.js` | 0→20 ใน 2 นาที, 20 คงที่ 6 นาที, 20→0 ใน 1 นาที (รวม 9 นาที) | `p(95)<800ms`, `p(99)<1500ms`, `http_req_failed<1%`, `checks>99%` | 20 VU ≈ 10 req/s เป็นจำนวนลูกค้าพร้อมกันที่สมเหตุสมผลของร้านเล็กที่มีสินค้า 18 รายการ ตอนโหลดเบา response time ปกติอยู่ที่ 150–320 ms (วัดด้วย curl) จึงตั้ง p95 ที่ 800 ms ให้มีที่เผื่อ แต่ยังต่ำกว่า 1 วินาทีซึ่งเป็นจุดที่ผู้ใช้เริ่มรู้สึกว่าช้า ส่วนโหลดปกติไม่ควรมี error เกิน 1% |
| `stress_test.js` | ขึ้นเป็นขั้น 20 → 40 → 60 → 80 → 100 VU (แต่ละขั้น ramp 1 นาที + คงที่ 1.5 นาที) แล้วลง 1 นาที (รวม 13.5 นาที) | รวมทั้ง test: `p(95)<2000ms`, `failed<5%` · แต่ละระดับโหลด `{load:Nvu}`: `p(95)<1000ms`, `failed<1%` | ไปถึง 5 เท่าของโหลดปกติเพื่อหาจุดที่ระบบเริ่มมีปัญหา threshold รวมยอมให้ช้าลงได้ตอนถูก stress ส่วน threshold รายระดับใช้เกณฑ์ "ยังดีอยู่" คือ 1 วินาทีและ 1% **ระดับแรกที่ไม่ผ่านคือจุดที่ระบบเริ่มมีปัญหา** |
| `soak_test.js` | 15 VU (75% ของโหลดปกติ) ramp 2 นาที, คงที่ 30 นาที (เปลี่ยนได้ด้วย `SOAK_MINUTES`), ลง 1 นาที | `p(95)<800ms`, `p(99)<1500ms`, `failed<1%` ทั้ง test และแยกทุกช่วง 5 นาที `{window:…}` | ใช้เกณฑ์เดียวกับ average load เพราะการรันนานไม่ควรทำให้ระบบแย่ลง การแบ่งช่วงละ 5 นาทีทำให้เห็นแนวโน้มว่า response time หรือ error rate เพิ่มขึ้นตามเวลาหรือไม่ ใช้ 15 VU เพื่อไม่ให้กินทรัพยากรของ server ที่ใช้ร่วมกันนานเกินไป |
| `spike_test.js` | 5 VU 1 นาที → พุ่งเป็น 100 VU ใน 10 วินาที → คงที่ 1 นาที → ลงเหลือ 5 VU ใน 10 วินาที → เฝ้าดู 3 นาที → ลงเป็น 0 ใน 10 วินาที (รวม 5 นาที 30 วินาที) | รวม: `p(95)<3000ms`, `failed<10%` · แต่ละช่วง `{phase:…}`: `p(95)<1000ms`, `failed<1%` | จำลองลิงก์ flash sale ที่ถูกแชร์จนคนเข้าพร้อมกัน ระหว่าง spike ยอมให้ช้าและ error ได้มากกว่าปกติ หลัง spike แบ่งเป็นช่วงละ 30 วินาที (`after-000-030s`, `after-030-060s`, …) **ช่วง after-* ช่วงแรกที่ผ่านเกณฑ์ปกติคือเวลาที่ระบบกลับมาให้บริการได้ตามปกติ** |

ป้าย `load`, `window` และ `phase` ทำให้ summary ของ k6 แสดง p(95) และ error rate แยกตามแต่ละระดับหรือแต่ละช่วงเวลา (ดูหัวข้อ THRESHOLDS ใน summary)

## วิธีรัน

```bash
cd "project phase 2/Performance testing"
./run.sh average_load_test
./run.sh stress_test
./run.sh spike_test
./run.sh soak_test                 # 33 นาที
SOAK_MINUTES=60 ./run.sh soak_test # ถ้าอยากรันนานขึ้น
SMOKE=1 ./run.sh stress_test       # รันสั้นๆ 2 VU เพื่อเช็ก script หรือใช้สาธิตตอนนำเสนอ
```

`run.sh` บันทึกวันเวลาเริ่มและจบไว้ในไฟล์ `results/<test>-<YYYYMMDD-HHMM>.txt` (summary ของ k6) และ `.json` (summary เดียวกันในรูปแบบ JSON) ถ้า exit code เป็น 99 แปลว่ามี threshold ที่ไม่ผ่าน

> server นี้ทุกกลุ่มใช้ร่วมกัน ควรรัน stress และ spike ทีละ test และไม่รันพร้อมกัน

## คำตอบจาก K6 metrics

ตัวเลขทั้งหมดมาจากไฟล์ใน `results/` ของการรันวันที่ 2026-11-03 ข้างบน

**a. ระบบรองรับ VU ได้สูงสุดกี่รายก่อนที่ response time จะเกิน 1 วินาที**

**20 VU** เป็นระดับสูงสุดที่ p95 ยังต่ำกว่า 1 วินาที จุดที่ response time เกิน 1 วินาทีอยู่ระหว่าง 20 ถึง 40 VU

| ระดับโหลด (ช่วงคงที่ 90 วินาที) | avg | p90 | p95 | max | request | throughput | failed |
|---|---|---|---|---|---|---|---|
| 20 VU | 123 ms | 195 ms | **226 ms** ✓ | 543 ms | 1,001 | 11.1 req/s | 0% |
| 40 VU | 485 ms | 915 ms | **1.14 s** ✗ | 2.17 s | 1,676 | 18.6 req/s | 0% |
| 60 VU | 1.63 s | 2.90 s | **3.48 s** ✗ | 5.91 s | 1,624 | 18.0 req/s | 0% |
| 80 VU | 3.04 s | 5.45 s | **6.11 s** ✗ | 8.07 s | 1,530 | 17.0 req/s | 0% |
| 100 VU | 4.45 s | 8.19 s | **9.22 s** ✗ | 15.25 s | 1,506 | 16.7 req/s | 0% |

ที่ 40 VU ค่า p90 ยังอยู่ที่ 915 ms และ p95 เกินไปเพียงเล็กน้อย (1.14 s) แปลว่าขีดจำกัดจริงน่าจะใกล้ 40 VU มากกว่า 20 VU แต่ stress test ขึ้นทีละ 20 VU จึงตอบได้ว่าระดับที่ทดสอบแล้วและยังผ่านคือ 20 VU

**b. ใน stress test ระบบเริ่มแสดงปัญหาเมื่อมี VU จำนวนเท่าใด**

**40 VU** เป็นระดับแรกที่ไม่ผ่าน `http_req_duration{load:40vu}` (p95 = 1.14 s > 1 s)

อาการที่พบคือ **ช้าลงอย่างเดียว ไม่มี error** ทุกระดับมี `http_req_failed` = 0% และ check ผ่าน 100% (18,995 จาก 18,995) ไม่มี 5xx และไม่มี timeout

จากตารางข้อ a เห็นว่า throughput เพิ่มจาก 11.1 req/s (20 VU) เป็น 18.6 req/s (40 VU) แล้วไม่เพิ่มอีก (60–100 VU อยู่ที่ 17–18 req/s) แปลว่า server ตอบได้มากที่สุดประมาณ **18 request ต่อวินาที** เมื่อมีผู้ใช้มากกว่านั้น request ที่เกินจะต้องรอคิว response time จึงเพิ่มตามจำนวน VU (avg 0.49 → 1.63 → 3.04 → 4.45 วินาที) สาเหตุที่เป็นไปได้คือจำนวน PHP worker หรือ CPU ของ server ไม่พอ เพราะทุก request ของ Store API ต้องรัน WordPress และ query ฐานข้อมูลใหม่ทุกครั้ง

**c. ใน soak test ค่า response time หรือ error rate แย่ลงเมื่อเวลาผ่านไปหรือไม่**

**ไม่แย่ลง ค่าคงที่ตลอด 33 นาที**

| ช่วง | 00-05 | 05-10 | 10-15 | 15-20 | 20-25 | 25-30 | 30-35 |
|---|---|---|---|---|---|---|---|
| p95 | 187 ms | 193 ms | 197 ms | 194 ms | 193 ms | 189 ms | 193 ms |
| avg | 109 ms | 110 ms | 112 ms | 111 ms | 109 ms | 107 ms | 111 ms |
| failed | 0% | 0% | 0% | 0% | 0% | 0% | 0% |

ช่วงแรก p95 = 187 ms ช่วงท้าย p95 = 193 ms ทุกช่วงต่างกันไม่เกิน 10 ms (±3%) ซึ่งเป็นความแกว่งปกติ ไม่ใช่แนวโน้มที่เพิ่มขึ้น error 0% จาก 16,032 request จึงไม่พบอาการ memory leak หรือการช้าลงจากข้อมูลตะกร้าที่สะสม (ระหว่าง test สร้างตะกร้าใหม่ 2,672 ใบ) ช่วง 00-05 มีช่วง ramp-up และช่วง 30-35 มีช่วง ramp-down รวมอยู่ด้วย จำนวน request ของสองช่วงนี้จึงน้อยกว่าช่วงอื่น

**d. ใน spike test ระบบใช้เวลานานเท่าใดในการกลับมาให้บริการได้ตามปกติหลัง spike**

**ประมาณ 30–60 วินาทีหลังจาก VU ลดลงเหลือ 5** (ช่วง `after-030-060s` เป็นช่วงแรกที่ผ่าน)

| ช่วง | before | spike-up | spike | spike-down | after-000-030s | after-030-060s | after-060-090s … after-150-180s |
|---|---|---|---|---|---|---|---|
| p95 | 182 ms ✓ | 13.44 s ✗ | 7.53 s ✗ | 6.01 s ✗ | 1.87 s ✗ | **177 ms ✓** | 173–187 ms ✓ |
| request | 84 | 191 | 1,010 | 169 | 256 | 84 | 80–86 |
| failed | 0% | 0% | 0% | 0% | 0% | 0% | 0% |

ช่วง `after-000-030s` ยังช้าอยู่ (p95 1.87 s) และมี request ถึง 256 รายการ ทั้งที่ 5 VU ปกติส่งแค่ประมาณ 84 รายการต่อ 30 วินาที เพราะ VU ที่ถูกลดออกจะยังทำ iteration ที่ค้างอยู่ให้จบก่อน (k6 รอได้สูงสุด 30 วินาที) เมื่อ request ที่ค้างหมดแล้ว ตั้งแต่ช่วง `after-030-060s` response time กลับไปเท่ากับก่อน spike (177 ms เทียบกับ 182 ms) ทันที ระหว่าง spike ไม่มี request ใดล้มเหลวเลย (0 จาก 2,160) แต่ผู้ใช้บางคนต้องรอนานถึง 15 วินาที ซึ่งในการใช้งานจริงผู้ใช้หลายคนน่าจะปิดหน้าเว็บไปก่อน

**e. ค่า `http_req_failed`, `http_req_duration` และ `vus_max` บอกอะไรเกี่ยวกับระบบในแต่ละการทดสอบ**

| Test | vus_max | http_req_duration (avg / p95 / max) | http_req_failed | การตีความ |
|---|---|---|---|---|
| Average | 20 | 115 ms / 210 ms / 1.31 s | 0.00% (0 / 5,118) | โหลดปกติรับได้สบาย p95 ต่ำกว่าเกณฑ์ 800 ms เกือบ 4 เท่า p99 = 311 ms มีเพียงบาง request ที่ช้าถึง 1.31 วินาที |
| Stress | 100 | 1.95 s / 5.82 s / 15.25 s | 0.00% (0 / 12,664) | เกิน 40 VU ระบบช้าลงตามจำนวนผู้ใช้เพราะ throughput ตันที่ประมาณ 18 req/s แต่ไม่ปฏิเสธ request เลย คือ server ต่อคิวไว้แทนที่จะตอบ error |
| Soak | 15 | 110 ms / 193 ms / 629 ms | 0.00% (0 / 16,032) | ใช้งานต่อเนื่อง 33 นาทีแล้วไม่ช้าลงและไม่มี error ระบบเสถียร ไม่พบ memory leak |
| Spike | 100 | 2.51 s / 7.48 s / 15.26 s | 0.00% (0 / 2,160) | เมื่อผู้ใช้เพิ่มจาก 5 เป็น 100 ใน 10 วินาที ผู้ใช้ต้องรอนานแต่ไม่มี request ล้มเหลว และระบบกลับมาปกติเองภายใน 1 นาทีโดยไม่ต้อง restart |

- `vus_max`: จำนวน VU สูงสุดที่ k6 จัดเตรียมไว้ หรือโหลดสูงสุดที่ระบบเจอใน test นั้น
- `http_req_duration`: เวลาตั้งแต่ส่ง request จนได้ response ครบ ค่า p95 สำคัญกว่าค่าเฉลี่ย เพราะบอกว่าผู้ใช้ 5% ที่โชคร้ายที่สุดต้องรอนานแค่ไหน
- `http_req_failed`: สัดส่วน request ที่ได้ status 4xx/5xx หรือเชื่อมต่อไม่ได้ ถ้าตัวเลขนี้เพิ่มขึ้นพร้อมกับ VU แปลว่า server รับโหลดไม่ไหว (เช่น PHP-FPM worker เต็ม)

**สรุป:** ระบบเสถียรและไม่มี error ในทุก test แต่ปัญหาคือความเร็ว server ตอบได้ประมาณ 18 request ต่อวินาที หรือประมาณ 20–40 ผู้ใช้พร้อมกัน เกินจากนั้น response time เกิน 1 วินาที ถ้าต้องรองรับผู้ใช้มากขึ้น ควรเพิ่ม PHP worker หรือ CPU หรือเพิ่ม cache ให้ API ที่ดึงข้อมูลสินค้า
